1. PROJECT OVERVIEW AND AUDIT SCOPE
--------------------------------------------------------------------------------
1.1 System Identity & Core Purpose
CMOS (Creative & Motion Operations System) / Orbiz ERP is a specialized internal
enterprise enterprise operations management platform engineered for end-to-end
coordination between Account Executives (Requesters), Creative Directors
(Team Leads), Creative Strategists (Strategic PICs), Graphic Designers (GD PICs),
Motion Graphic Designers (Motion PICs), and Live Streaming Broadcast Teams
(Operators).

The platform tracks creative tasks from initial brief submission, concept
ideation, static graphic design production, and approval through to automated
handover for motion graphic animation and live streaming broadcast checkout.
It additionally enforces Service Level Agreements (SLAs), measures team capacity
via difficulty-weighted point models, archives completed weekly deliverables,
and synchronizes request metadata in real time to external Google Spreadsheets.

1.2 Audit Scope & Methodology
This audit was performed via a dual-methodology approach:
a) Static Source Codebase Inspection:
   Direct AST and line-by-line review of all 25 Next.js App Router routes,
   shared layout trees, utility engines, database connectors, and state stores.
b) Dynamic Runtime & Visual Inspection:
   Live browser exploration of the active local development server
   (http://localhost:3000) using multi-role personas (System Administrator,
   Team Lead, Graphic Designer, Motion Designer). Both Light and Dark theme
   states were audited alongside mobile, tablet, and ultra-wide viewports.

1.3 Non-Destructive Constraint
This document represents an audit and redesign specification. In accordance with
the strict execution guidelines, NO application source code, business rules,
PostgreSQL database schemas, migration files, or API contracts have been modified.

2.3 Operational Workflows & Business Rules Discovered
1. Four Distinct Pipelines:
   - STRATEGIC: For early conceptual creative work. Tasks have StratStatus
     (PENDING, IN_PROGRESS, REVIEW, REVISION, APPROVED). Assigned to Strategic PIC.
   - GD_MOCKUP: Promotional mockup assets. Originates from Orca or E-commerce.
     Has DesignStatus (UNASSIGNED, ASSIGNED, IN_PROGRESS, SUBMITTED, REVISION,
     APPROVED). Can auto-handover to Motion once approved.
   - GD_NON_MOCKUP: E-commerce marketplace assets (Shopee/TikTok feeds, banners).
     Does not transition to Motion. Terminal status is APPROVED/CLOSED.
   - MOTION: Animation tasks. Either Standalone or Auto-Handover from approved
     GD_MOCKUP. Tracks difficulty (LVL 1-4) and MotionStatus (QUEUED, IN_PROGRESS,
     SUBMITTED, REVISION, APPROVED, COMPLETED).
2. Difficulty Weighting System:
   - Design: LOW (2.5 pts), MEDIUM (3.5 pts), HIGH (4.5 pts).
   - Motion: LVL 1 (2.0 pts), LVL 2 (3.0 pts), LVL 3 (4.0 pts), LVL 4 (5.0 pts).
   - Capacity Thresholds: Staff (7.0 pts/day = 140 pts/month), Intern (5.0 pts/day).
3. SLA Operational Excellence:
   - Calculated in net business days excluding weekends and configured holidays.
   - <= 3 business days = EXCELLENCE
   - 4 - 5 business days = GOOD
   - > 5 business days = BAD
4. Weekly Partition Archiving:
   - Approved tasks are automatically grouped by year-month-week
     (e.g., "2026-10-W3" based on due date / completion date).
   - Keeps active kanban boards clean while retaining full searchability.

6. CURRENT UI/UX ASSESSMENT
--------------------------------------------------------------------------------
6.1 Visual Hierarchy
- Problem: Screen elements compete aggressively for user attention. On Kanban
  cards, task titles, difficulty badges, client tags, and SLA badges all use
  high-saturation saturated backgrounds.
- Impact: High cognitive fatigue for designers managing 20+ cards daily.

6.2 Readability & Typography
- Problem: Excessive font size variation (ranging from 8px micro-badges to 24px
  KPI text). Several metadata elements use font sizes below 11px, failing
  comfort standards for desktop display viewing.
- Impact: Operators and designers struggle to scan timestamps and due dates
  quickly during busy shifts.

6.3 Information Density & Clutter
- Problem: Filters and cards attempt to expose every single database field
  simultaneously. On the Capacity page, 9 dropdowns push operational metrics
  off-screen.
- Impact: Wasted vertical screen space and unnecessary scrolling.

6.4 Navigation & Usability
- Problem: Redundant navigation paths (Pipeline links in sidebar AND in page
  body). Inconsistent placement of the user profile (bottom of sidebar instead
  of standard enterprise top-right header).
- Impact: Confusion regarding active location and unnecessary mouse travel.

6.5 Consistency
- Problem: Mixed language usage (Indonesian and English intermingled in filter
  dropdowns, e.g., "All Months" next to "Semua Role").
- Impact: Unpolished, amateur appearance inconsistent with high-grade enterprise software.

6.6 Accessibility (WCAG 2.2 AA)
- Problem: Status is sometimes communicated solely through color (e.g. green/red
  dots without text labels). Several icon-only buttons lack `aria-label` attributes.
  Dark mode contrast on secondary text (var(--text-muted): #6B7280 on #141619)
  drops to ~3.8:1, falling below the WCAG AA minimum requirement of 4.5:1.
- Impact: Fails accessibility standards for visually impaired team members.

6.7 Responsive Design
- Problem: At tablet (768px - 1024px) viewports, topbar controls overlap, and
  Kanban column headers get cramped. On mobile, modals take up full width but
  have awkward padding.
- Impact: Mobile operational checkouts by Account Executives are frustrating.

6.8 Interaction Feedback
- Problem: Modal action buttons sometimes lack inline loading spinners during
  asynchronous database writes, causing users to double-click submit buttons.
- Impact: Risk of duplicate form submissions and user confusion.

8. TARGET DESIGN PRINCIPLES
--------------------------------------------------------------------------------
1. Restrained Enterprise Aesthetics:
   Clean, flat, high-contrast surfaces inspired by Linear, Vercel, and GitHub.
   Zero glassmorphism, zero decorative gradients on cards, zero floating blobs.
2. Purposeful Semantic Color:
   Neutral backgrounds (grays, slates) with color reserved strictly for meaning:
   - Emerald  : Approvals, SLA Excellence, Synced state.
   - Amber    : Warnings, Due Today, Revisions, Optimal capacity.
   - Red      : Overdue tasks, SLA Bad, Destructive actions.
   - Blue     : Primary brand actions, In Progress states.
   - Purple   : Strategic concept workflows.
3. Rapid Information Scanning:
   Card and table layouts designed for sub-second recognition of:
   - What brand is this for?
   - Who is working on it?
   - When is it due?
   - What is the blocker/status?
4. Progressive Disclosure:
   High-level metrics and cards visible by default; deep audit logs, full brief
   descriptions, and chat history accessible via contextual modals and drawers.
5. Absolute Functionality Preservation:
   The visual redesign must not alter any existing database queries, SLA math,
   pipeline routing, or role-based access rules.

14. ACCESSIBILITY REQUIREMENTS (WCAG 2.2 AA)
--------------------------------------------------------------------------------
1. Contrast Compliance:
   All text against surfaces must achieve at least 4.5:1 for normal body text
   and 3:1 for large display text and UI components.
2. Visible Keyboard Focus:
   Every interactive element (buttons, links, inputs, dropdowns) must display
   a high-contrast focus ring: `outline: 2px solid var(--accent-blue); outline-offset: 2px`.
3. Screen Reader Semantics:
   - Icon-only buttons must include explicit `aria-label` (e.g. `aria-label="Tutup modal"`).
   - Dynamic alert panels must include `role="alert"` and `aria-live="polite"`.
4. Non-Color Status Cues:
   Overdue tasks must display both a red highlight AND an explicit text label
   `OVERDUE (+Nd)` alongside a warning icon.
5. Modal Focus Trapping:
   When any modal opens, focus must automatically move to the first interactive
   element, and focus must return to the trigger button when closed.

19. RISKS, DEPENDENCIES, AND LIMITATIONS
--------------------------------------------------------------------------------
1. Browser Bundler Boundary Risk:
   - Ensure server-side Google Auth dependencies (`child_process`, `fs`) remain
     isolated in `google-sheets-server.ts` and are never imported by client components.
2. HTML5 Drag-and-Drop Limitations:
   - HTML5 drag events are native to desktop mice. Touch devices should rely on
     the accessible status transition dropdown inside the task modal rather than
     forcing complex touch polyfills.
3. Google Sheets External Rate Limits:
   - Google Sheets API v4 enforces a quota of 300 write requests per minute per project.
     The transactional outbox queue with bounded backoff effectively mitigates this.
4. Tailwind CSS v4 Migration Nuance:
   - Tailwind v4 uses `@import "tailwindcss"` without a traditional `tailwind.config.js`.
     Design tokens must continue to be declared as CSS custom properties in `globals.css`.
